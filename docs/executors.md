# Typed actions, executors and session records

For whoever runs an executor or looks for a running session: what the queue holds, and what a session record says.

## Typed next actions and stateless executors

The control plane names what each item needs next as one typed action and keeps a durable leased row for it, so a master session is not the planner and need not be running ([the model](architecture.md#inverted-coordination-typed-actions-and-stateless-executors)). The nine kinds are `dispatch`, `request-review`, `request-rework`, `approve-scope`, `resync`, `reclaim`, `merge`, `verify-deployment` and `escalate`; an item with nothing named needs nothing from anybody.

| Where to read it | What it holds |
| --- | --- |
| `master status` → `actions` | What each open item needs, which executor holds which row and since when, and every row past the five-minute idle bound |
| `actions.stalled` | Each stalled row's unchanged reason, the failures that shared it, its attempts and when it is offered again; one attention item per stall, addressed to the master, and on the item's dashboard card in place of the gate sentence it was going to clear |
| `actions.backoff`, `actions.open` | The rows waiting out a backoff, and the count in which `pending + claimed + settling + backingOff` accounts for all of them |

`node scripts/graphyard-executor.mjs [--once] [--kinds merge,resync]` reads this host's `.graphyard/master.json` for the launch profiles and authenticates with the coordinator credential named there, nothing broader; run as many as you like, on as many hosts, none of them a master. It refuses to start with a handler for `escalate` or `request-rework`, which are judgements made in the step itself. Its routes are `POST /api/actions/claim`, `POST /api/actions/[0-9a-f]{32}/(settle|renew)` and `GET /api/actions` — the queue, the computed actions, open requests and running sessions, with `kind` narrowing it — while `POST /api/work/*/resync` schedules the provider reading `resync` and `reclaim` mean. A claim is a two-minute lease and the handlers are not two-minute operations, so an executor inside one renews every thirty seconds; only the executor named on the claim, holding the credential it was made with, may renew, and only while it is live. Any number of executors and `master run` share one control plane without coordinating: the queue serializes the rows and every merge is brokered under its own execution instance, so one finding a foreign execution stands down and retries. A free worker asks for its own next assignment with `node scripts/graphyard-pull.mjs [--watch]` (`POST /api/assignments/claim`), which offers the items already named as needing a dispatch, in dispatch order, claimed under the worker's own identity through every ordinary claim rule.

## Typed requests instead of prose questions

A session that needs something records a typed request and exits, giving up its lease in the same transaction, so the item is free instead of held at a prompt: `POST /api/work/GY-N/request` with a `type`, the asking `epoch` and its payload (`{"type": "scope-request", "epoch": 3, "paths": ["docs/"], "reason": "…"}`). Recording one is the same write as the command it replaces — a `blocker` sets the blocker the ready gate reads, an `escalation` fences every in-flight merge — so it needs the live lease of the attempt asking; only a `note`, which moves nothing a gate reads, may be recorded without one, and closing a request is the decider's, never the asker's. Each type names one decider: a `scope-request` the additive planned-files rule, applied in the same transaction so a refusal becomes the item's blocker; a `decision` and an `escalation` an independent approver agent; a `blocker` a tracked follow-up item; a `note` nobody — unless the request names one of the three human-only decisions, which routes to the operator whatever its type. `master status` lists every open request with its decider, the command that answers it and how long it has waited; a session that ends waiting on input instead is recorded as failed, naming the request it should have made.

## The dispatcher's own state

The dispatch cursor (`*.dispatch.json` beside the coordinator credential) holds the tick count, the last tick's counts and the reasons nothing launched, every refused launch with its widening retry, and each role's capacity hold. Every string is bounded where it is composed, each cut marked with an ellipsis, and the bounds nest — a stored failure reason (300 characters) leaves room for the wait sentence wrapping it, itself bounded (500) before it becomes a tick reason — so a cursor that fails its schema is repaired rather than fatal: an over-long string is truncated in place on load and before every persist, the repair logged once with the failing path, while anything else the schema refuses is refused by path and a cursor `master status` cannot read is one attention item. `dispatch.lastFailure` names the `field` it could not write with the `kind`, `request` and `work` it was composed for, beside `consecutiveFailures` and `lastSuccessAt`; three consecutive failures raise one attention item, addressed to the master, saying no reviewer or producer session is being launched for any item and why, with the repair path (`graphyard master restart`) or the fault to fix.

**A session that exits at launch is classified from its pane,** read only as often as the launcher reads it. A provider limit notice is account exhaustion: refused within seconds rather than at the bound, recorded for the account the launcher selected (`profile:NAME` for a profile naming no `accounts`), and failed over as a [mid-session exhaustion](fleet.md#exhaustion-in-the-middle-of-a-session) is, the tick listing each account passed over under `failover`. A runtime Herdr found at a dialog did not exit and is not; any other cause is the refusal the launcher worded, retried on the widening schedule.

## Session handles and liveness

Every launched session records a durable handle on the item — runtime, host, Herdr workspace, tab and pane, its transcript, and what it is working on — under `sessions` in `master status` and in the dashboard drawer, each with the one command or link that attaches to it (`herdr pane attach PANE`, or the transcript once finished). Every launcher records one; what only the session knows it adds itself with the `session` work command (`POST /api/work/GY-N/session`), and a handle merges field by field. Writing one is authority, because the attach command is an instruction somebody runs: an existing handle belongs to the session it names, its launcher or an admin, and creating one belongs to the implementation session under the epoch it holds or — with no epoch — to its launcher or the session of a live dispatch request whose id it carries, so nothing else can squat a predictable id or push a running session off the bounded list.

**The control plane reconciles session liveness; closing finished sessions is nobody's manual duty.** The sweep runs on every automatic-dispatch tick (`run.dispatchIntervalSeconds`), leaving a handle the runtime no longer reports alone for a 60-second grace — counted from the first sweep that missed it, never shorter than the handle's own age — so a vanished record closes within 90 seconds, and `dispatch.sessionReconcile` carries the bound, the last tick's closures, the handles inside their grace and any closure it could not write back. A closure names why — **vanished**, **ended** (a terminal state of that runtime in `src/harness.ts`, which today only Muse has; `idle`, `done` and `blocked` are terminal nowhere, each being a live session at its prompt), **superseded** (a review or proof session bound to what the item moved past, never an implementation session) or **duplicate** (one live review of a head, one producer session per proof group) — and is a record, never authority: it decides no gate, ends no lease and stops no process. A session Herdr reports blocked is waiting on input, not gone, so its handle stays `running` carrying why, and one running without progress is not closed either: `master status` raises one attention item per session past its role's maximum — 4h implementation, 1h review, `run.producerTimeoutMinutes` for a producer, 12h coordination — naming the item, the role, how long it has run and whether the runtime still reports it live. `master run --once` sweeps once when the loop is stopped; never mark another session's handle finished to free a slot.
