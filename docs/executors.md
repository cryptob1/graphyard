# Launching and tracking agent sessions

For whoever asks why a session did not start, or looks for one that is running: how a launch reaches its runtime, and what a session record says.

## Automatic dispatch at submit

The control plane [records under `autoDispatch`](protocol/github-webhook.md#automatic-dispatch-at-submit) what the exact head needs; the loop launches it.

- **Requests:** one review per head the policy expects a GitHub verdict for; one producer per proof group (`unit`, `integration`, and `manual` for proofs in `producerProofs`) no trusted passing evidence binds. A group whose trusted evidence already failed on this head is a finding to route, not a run to repeat
- **Launch cadence:** within 30 seconds of the request, then every `dispatchIntervalSeconds` — the reviewer profile (`run.reviewerProfile`, or the only one) and one producer session per proof group on a free, independent producer profile ([template](../examples/master/claude-producer.json)), up to each profile's [concurrency](fleet.md#per-role-concurrency); with fewer free slots than groups the rest wait and `master status` names the limit
- **Producer identity:** its credential authenticates exactly its principal as a producer, never shares a principal with a worker profile, and is skipped for an item its principal implemented. The session reads it from `GRAPHYARD_TOKEN_FILE`, works in the detached worktree of its own [session checkout](fleet.md#session-checkouts), and submits each proof against that binding, a failing run as `fail`
- **One session per request:** `.graphyard/reviews.json` and `.graphyard/producers.json` record which request each session answers. A session Herdr reports finished, gone or blocked on a prompt for five minutes without a verdict or evidence is `failed`, relaunched at most four times; `master review GY-N [PROFILE]` recovers an exhausted one. A reviewer first seen stopped is prompted once, in place, to post the verdict it judged, those five minutes running from that sight — never by a master's own hand
- **The master's half:** findings, rework and merges; it never launches reviews or producers by hand, never approves a candidate, never submits evidence. A request nothing answers — a dismissed approval, or a session that settled without a verdict — stays open and is [attention, not silence](github.md#dismissed-approvals-and-unanswered-requests)
- **Profiles and attention:** `master producer add FILE`, `master producer replace FILE`, `master producer remove NAME`, `master reviewer remove NAME`, and `concurrency` in either profile; `setup.attention` reports a reviewer App registered but never bound, a bound App whose credential file is gone, and a `herdrWorkspace` Herdr no longer lists

### The request is the session's first message

Every session Graphyard launches — worker, reviewer, producer, approver, master — takes its instruction as its own first request on the runtime's command line: positional after the flags for Claude Code, Codex and Cursor, `--prompt` for OpenCode. `master status` reports `delivery: request`, or `paste` for a runtime with no request contract.

- **Not typed into the pane:** the launcher writes the request, and for a Claude Code session under a role file the launch authorization, to `.graphyard/launch/NAME.request` and `NAME.role` (mode 0600) inside that session's own checkout — the worker's assigned worktree, a reviewer's or producer's session checkout, or the repository root for the master, an approver and an escalation handler — and types one short line referencing them through their shared stem, `GY=…/.graphyard/launch/NAME; claude … --append-system-prompt-file "$GY.role" "$(cat "$GY.request")"`, which the pane's POSIX shell expands before the runtime starts, so the request is still the runtime's own first argument and never a paste. A worker's line carries the same references after `node CLI watch GY-N EPOCH -- KIND`. What is typed is bounded at **512 bytes**; a longer line is refused before anything is typed, naming its length, which only a very long repository path, worktree root or `agentArgs` can cause. The files are rewritten on every launch under the same name and removed with the checkout
- **The pastes left:** a paste-only runtime's request, the loop's one re-prompt, the reviewer's verdict reminder — the launcher repeating the session's own request ([what that authorizes](onboarding.md#what-the-generated-instructions-authorize)). One counts only when Herdr sees the runtime leave `idle`: delivered three times at most, then the session is closed, a worker's claim released, and relaunched once from scratch before the launch is reported refused
- **Started is read from the pane** every half second (`herdr agent get` for the runtime and state Herdr sees, `herdr pane read` for the text). **Ready** is the expected kind `idle`, `done` or `working`, or the runtime under the pane in any state while its own screen shows — banner, status line or spinner (`∙ ✻ ✶ ✳ ✢`) at the start of a line; a runtime with no request contract is ready only on `idle` or `done`. **Starting** is its process existing with nothing drawn yet, **blocked** a dialog before it was ever ready, which no launcher answers, and **absent** none of these. Ready within **30 seconds** has started (`started.detail`); *starting* at 30 seconds is given up to a **120-second** ceiling (`started.extended`); *absent* at 30 seconds, or still starting at the ceiling, is refused naming the case and the pane's last non-empty line (bounded to 200 characters) rather than Herdr's own `agent_not_found` — `the claude runtime never started within 30 s in pane w1V:pR6 (command still echoing); the pane last showed: "…"`, `(no runtime under the pane)`, `was still starting after 120 s …`, `is blocked before it is ready …`. The tab is closed and the checkout removed; a pane showing a provider limit notice is a [failover](fleet.md#exhaustion-in-the-middle-of-a-session), not a refusal
- **Acknowledged:** `session.activity` is `awaiting acknowledgement` (`counts.dispatchAwaiting`, beside `counts.dispatchRunning`) until Herdr sees activity — `working`, `blocked`, or a screen changing under a long command — across thirty seconds of consecutive sightings (`acknowledgedAt`), or a verdict or evidence exists. A session quiet for `run.acknowledgementSeconds` (30–900, default 90) is sent its request again, once (`repromptedAt`, the row's `attention`), restarting the window
- **`never started: …`:** a session settling still unacknowledged, quoting the last words `finished (done) without …` also carries. A failed launch is not failed work: it is relaunched a minute later, outside the four attempts and the widening wait, three exhausting the request (`retry.neverStarted`, `retry.unstartedLimit`), and never settled before its re-prompt and the interval after it, whatever the five-minute grace; `run.producerTimeoutMinutes` (at least 5) bounds it all

#### How the request reaches the runtime

The request is not typed into the pane: several kilobytes of it would spend the whole start bound echoing. The launcher writes it — and, for a Claude Code session under a role file, the launch authorization it would otherwise pass as `--append-system-prompt` — to `.graphyard/launch/NAME.request` and `NAME.role`, mode 0600, inside the session's own checkout, and types one short line referencing them through their shared stem:

```
GY=/path/to/checkout/.graphyard/launch/NAME; claude --permission-mode bypassPermissions --append-system-prompt-file "$GY.role" "$(cat "$GY.request")"
```

The pane's POSIX shell expands it before the runtime starts, so the request is still the runtime's own first argument and never a paste; a worker's line carries the same references after `node CLI watch GY-N EPOCH -- KIND`. What is typed is bounded at **512 bytes** whatever the request is, a longer line refused before anything is typed, and the files are replaced on every launch and removed with the checkout.

#### The start bound reads the pane

The launcher reads the pane every half second — `herdr agent get` for the runtime and state Herdr sees, `herdr pane read` for the text. The runtime is **ready** on the expected kind `idle`, `done` or `working`, or under the pane in any state while its own screen shows; **starting** with its process up and nothing drawn; **blocked** at a dialog no launcher answers; **absent** otherwise. Ready within **30 seconds** has started (`started.detail` naming the sighting, `the claude runtime is on screen while Herdr reports it unknown`); one still starting gets up to **120 seconds** (`started.extended`); *absent* at 30 seconds, or still starting at the ceiling, is refused with the case and the pane's last non-empty line (200 characters), never Herdr's own `agent_not_found` — `the claude runtime never started within 30 s in pane w1V:pR6 (command still echoing)`, `(no runtime under the pane)`, `was still starting after 120 s`, `is blocked before it is ready`. The refusal is recorded wherever launches are (`Automatic producer launch for GY-N refused 1 time(s): …`), the tab closed and the checkout removed.

#### The dispatcher's own state

The dispatch cursor (`*.dispatch.json` beside the coordinator credential) holds the tick count, the last tick's counts and the reasons nothing launched, every refused launch with its widening retry, and each role's capacity hold.

- **The dispatcher bounds its own state where it composes it.** Every string it writes is bounded before it is stored, each cut marked with an ellipsis, and the bounds nest: a stored failure reason (300 characters) leaves room for the wait sentence that wraps it, itself bounded (500) before it becomes a tick reason, so a launch failing with a 2,000-character error is a refusal ending in `…`, not a tick that cannot persist.
- **A cursor that fails its schema is repaired, not fatal.** On load and again before every persist a string past its cap is truncated in place and the repair logged once with the path that failed; anything else the schema refuses is still refused by path, and a cursor `master status` cannot read is one attention item rather than a dispatcher silently absent.
- **A tick failure is attributed and surfaced.** `dispatch.lastFailure` names the `field` it could not write with the `kind`, `request` and `work` it was composed for, beside `consecutiveFailures` and `lastSuccessAt`. Three consecutive failures raise one attention item, addressed to the master, saying that no reviewer or producer session is being launched for any item and why, with the repair path (`graphyard master restart`) or the fault to fix; every request keeps reading as `waiting` meanwhile.

**A session that exits at launch is classified from its pane.** `herdr agent get` answers `agent_not_found` while the runtime is not there, which says nothing about why, so the dispatcher watches each launch's own `herdr pane read` — no more often than the launcher reads it — and classifies from the last read. A **provider limit notice** is account exhaustion: the launch is refused at the launcher's next pause, within seconds rather than at the bound, recorded for the account the launcher selected (`profile:NAME` for a profile naming no `accounts`), and it fails over exactly as a mid-session exhaustion does ([exhaustion](fleet.md#exhaustion-in-the-middle-of-a-session)), the tick listing each account passed over under `failover`. A runtime Herdr found at a dialog did not exit and is not classified this way; any other cause is the refusal the launcher worded — which case it saw and the pane's last words — retried on the usual widening schedule. A session that exits **at launch** never waits out the 120-second ceiling for a notice already on the pane.
