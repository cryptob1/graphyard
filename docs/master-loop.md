# The durable coordination loop

For whoever runs `master run`: what the loop decides on its own, and what it will never do.

A chat session is a poor coordinator — its transcript grows without bound and it dies with its provider's credits — so the deterministic part of coordination runs as a supervised process ([which it must be](onboarding.md#the-loop-must-be-supervised); [flags and settings](operations-reference.md#master-coordination-loop)). Each cycle it re-reads the configuration, reclaims worktree disk, **settles the quarantine of a dead worker** it verified gone on the registered host, dispatches claimable work, requests the decisions below and watches each one, shepherds reviews and proofs, merges what every gate passes, verifies the deployed SHA, and records what it could act on and what it did. The configured interval is the idle cadence, not a bound: while anything is actionable the loop returns within thirty seconds. Restarting is always safe — a cursor is written before and after each external action and the next start resolves against Graphyard, not the cursor, so a landed assignment is closed, one that never landed is released, a review request is never sent twice, and an interrupted decision request adopts the request and approver session already standing.

## Unattended decisions

Each of these has one correct answer, so the loop makes it with the master's own two identities and no shortcut through the separation the server enforces. It never approves what it requested: the approver session judges from its own identity, and the server refuses self-approval, an approver that held an assignment on the item, and one that produced the evidence the decision rests on.

| What the loop sees | What it does | Who applies it |
| --- | --- | --- |
| A change request standing against the exact current head — a `CHANGES_REQUESTED` GitHub review, or an agent or Codex review carrying `verdict: changes-requested` for it | Requests `rework`, launches the approver session, dispatches the next attempt | The approver agent |
| A base branch the control plane could not merge into the candidate | Requests `rework` naming the conflict | The approver agent |
| A delivered item still fenced by a quarantine whose supervisor this host verified gone | Requests `recover` | The approver agent |
| Every gate green while automatic merging is off | Requests `merge` for that exact candidate, then merges once approved | The approver agent |
| A lapsed quarantine this host verifies dead | Settles it with the coordinator credential | The loop |
| An open scope request from the lease that raised it | Asks the control plane to decide it | The control plane |

A review that has not approved is not a verdict: the observers report `approved: false` for a review not yet dispatched, one still running, a retry, an unready pull request and exhausted profiles, so the loop acts only on the structural `verdict` set where the reviewer asked for changes on that exact head, never on a refusal's reason text. It attests only what it verified, so neither rework nor recovery is requested while a lease is live or a fence is inside its grace, and with the lease ended only when no fence stands or the same cycle's probe on the registered host verified that epoch's supervisor gone — the reason states which, and a lapsed fence the host could not verify withholds the decision and escalates with the probe's refusals (`decision-withheld`). A round is requested once, because a verdict or base conflict keeps matching its head until a new head is pushed.

`daemon.approvals` reads each requested decision back from the control plane and its session back from Herdr every cycle: it waits while the session works inside ten minutes; closes and replaces one gone, ended without approving (the only way a decline shows) or past ten minutes, at most three per decision; requests the decision again if it ended `failed`, `stale` or `withdrawn`, at most three per binding; and after three spent sessions escalates once with how each ended and `master approver GY-N DECISION`. A `merge` decision for an earlier candidate is withdrawn and re-requested for the current one, and one the item no longer calls for is withdrawn rather than adopted for a later round. Every generated session name is built inside the runtime's own limit — at most 32 characters, starting with a lowercase letter, of lowercase letters, digits, `-` and `_` — where it is constructed, so a profile whose `agentName` Herdr could not launch is refused when the profile is read, not after a pane was allocated, and a refused launch reports the limit, the name attempted and the command that retries it; an approver's is `graphyard-approver-<key>-<start of the decision id>`, and a key long enough to crowd that out shortens the role word (`gy-approver-<key>-<decision>`) before falling back to a digest. Without an operator-agent identity (`master autonomy --admin-token-stdin --apply`) the effects are simply not wired: each routine decision becomes an escalation naming the two commands a master session runs instead, picked up on the next configuration reload.

## Liveness and silence

**The loop's own liveness comes first on the attention list.** `daemon.liveness` is `running`, `stalled` (no completed cycle for more than two intervals) or `absent` (no lock, or a lock whose process is gone here), each with `master restart`. A supervised deployment needs no command: the packaged unit sets `Restart=always` with no start limit and the loop sends a keep-alive after every cycle, completed or failed, so a hung cycle is restarted as surely as a process that exits, while a loop waiting out a failed-cycle backoff announces its next cycle and reads as `running` until that is overdue by two intervals. `WatchdogSec` must stay longer than two cycle intervals; a window that would restart a healthy loop mid-cycle is recorded by name rather than obeyed. The keep-alive is `systemd-notify`, admitted by `NotifyAccess=all`; on systemd older than 246 one can be lost to a race, which is why the packaged window is 180 seconds against a cycle of at most thirty.

**Silence is measured against what the loop could act on.** Every cycle records the actionable inventory — claimable work, a routine decision from the moment the item needs it until it is applied, a scope request, a settleable quarantine, a mergeable candidate, a proof missing on a head no verdict stands against, a pending base refresh, a delivery awaiting its deployment or smoke — and the actions taken. A subject's wait restarts only when an action succeeds, so a request the server refuses on every retry reaches the bound like any other silence; `daemon.silence.longestIdleMs` carries the longest wait with its subject, and past twenty minutes it is an attention item. An item nobody is waiting on is not silence. `daemon.budget` reports each delivery budget with `met` and its reasons, measured from what the loop itself observed: ready → claim p90 at or under 2 minutes, ready → first push p90 at or under 15 minutes, approval → merge p90 at or under 10 minutes over at least ten deliveries, and the per-candidate bounds mergeable → merge and standing verdict → rework requested, both 5 minutes. `met` is null below ten measured deliveries, and a delivery is sampled once from the clock the loop kept while the item was open, so a recorded breach is never outvoted by the ledger's past.

### A cycle that fails

A rejection that escapes a cycle — a snapshot read aborting on its timeout, a failing Herdr command, a `.graphyard/master.json` reload that no longer parses — fails that cycle and nothing more: the process does not exit, the counter advances, the failure is written to the cursor and logged with its cycle number, and the next cycle runs after a delay. A hung cycle is the watchdog's to restart; a cycle that threw has just proved it did not hang. `daemon.failures` carries `consecutive` (failed cycles since the last completed one, which the backoff and the attention item read), `total`, `last` (its `cycle`, `at`, `phase` — `cycle` or `reload` — the `call` it escaped from, the runtime's `reason`, and the `delayMs` and `nextAt` chosen), `unhandled` and `lastUnhandled` (`origin`, `reason`, and the cycle it landed during); `master run --once` reports `failedCycles` and `lastFailure` beside `cycles`. The first failure waits the configured interval and each consecutive one doubles it, to a ceiling of five minutes, the interval when that is longer, or half the watchdog window under a supervisor with one; the first completed cycle resets the count while `total` keeps the history. Three consecutive failures raise an attention item at the head of the list naming the failing call and its reason and saying the loop keeps cycling in-process — its owner is the master, and the next command clears what that call refuses on, since a restart does not fix a read that times out every time. An unhandled rejection or uncaught exception anywhere in the process is caught, logged with its origin, counted under `unhandled` and survived; it is not a failed cycle, and only a stop signal ends the loop.

## Human-only waits

A worker whose item reaches one of the three decisions reserved to the human operator writes no prose blocker and keeps no lease: it records a **typed request** and stops.

```sh
node "$GRAPHYARD_CLI" park GY-N EPOCH money-or-accounts A Hetzner Cloud project with an API token for the live-install proofs -- The proofs provision real servers; opening the account is the operator's
```

`KIND` is `goals-and-priorities`, `money-or-accounts` or `credentials-for-people`; the words before `--` are the exact thing needed, those after it the reason. That one transaction (`POST /api/work/GY-N/park`, the lease holder only) writes `humanRequest`, ends the attempt as `released`, sets the blocker `Waiting on a human-only decision (…): NEEDED` and appends `human.requested`. The session exits holding nothing, its supervisor's next renewal is refused, no `lease-loss` is raised, and the item is not claimable. Every open request is in one list — the dashboard's [Needs you](dashboard.md#needs-you) tab, `graphyard human-requests`, `GET /api/human-requests` and `humanRequests` in `master status`, whose attention item is addressed to the human — with the decision, the thing needed, the reason, who asked, how long it has waited and the command that answers it.

```sh
graphyard answer GY-N [REQUEST] The project exists; its token is in the ops vault under hetzner-ci
graphyard answer GY-N [REQUEST] --decline We are not opening a Hetzner account this quarter
```

Only a declared human `admin` session may answer (`POST /api/work/*/answer`); an agent holding an admin credential is refused. A provided answer clears the request and its blocker in one transaction (`human.answered`), leaving the item claimable, and **the loop dispatches it on its next cycle** with the answer in the new attempt's prompt. A declined answer keeps the item parked with the human's words as its blocker, for the master to re-scope.

## What the loop will not do

It runs on the coordinator credential and reads the master's operator-agent credential for exactly the requests above. It never reads the approver's credential, never approves a decision, never claims a lease, never submits evidence, never revises a requirement, never releases backlog work, and refuses to start if its coordinator credential may also produce evidence. Deciding a scope request is no exception: it asks, the control plane decides and applies, and a widening the item does not already imply comes back refused. Besides the guarded merge, the facts it writes are its own deployment observation on a delivered item, the settlement of a quarantine it verified on this host, and what it observed about provider capacity; the smoke verdict comes from the workflow's producer. Provider exhaustion, a failing reviewer, a missing manual proof and an unhealthy worker profile are escalations, never shortcuts, and a refused merge is the gate working. Everything else is still a judgement and reaches `master status` with its owner and next command.
