# Shipping pulse

Shipping pulse summarizes repository delivery flow. It is deliberately a repository view, not a worker scorecard: it contains no rankings, lines of code, effort estimates, individual productivity measures, or causal claims.

## Source and definitions

Every value comes from the append-only `events` ledger. A delivery is counted only from the first `github.observed` event for a work item whose immutable event payload contains an accepted `delivery`, exact pull request, exact merge commit, and provider merge timestamp. Mutable `work_items` snapshots, claims, submissions, lease activity, and inferred implementation activity are never counted.

A work item is delivered once, and which event records that delivery is decided across the whole ledger before any reporting window is applied. Later events carry the work document forward, so a re-observation months after a merge still contains a `delivery`; deciding the first delivery event inside the window would make such a snapshot look like a fresh delivery, counting a second delivery for an item that shipped once and filing it under the wrong week. The query therefore narrows in-window candidates to the earliest per work item, then keeps only those that are also the globally first delivery event for that item — one exact `events_delivery_first` probe keyed `(work_id, seq)` over delivery-bearing events, so the check is a single index tuple per candidate rather than a walk of the item's history. A work item whose first delivery lies before the window contributes nothing to it, however many later snapshots fall inside.

Delivery timestamps are read through `graphyard_instant`, an immutable SQL function that resolves an RFC3339 value to an instant, subtracting an explicit numeric offset and otherwise reading the value as repository UTC. The repository PostgreSQL clock defines “now” and all boundaries use UTC.

GitHub's merge timestamp is GitHub's own clock, and the repository clock is the database's. The two are related only through the bounded offset measured at merge verification, which refuses an observation wider than twenty seconds; the offset's magnitude is not bounded, only how precisely it is known. A delivery therefore records both: `delivery.mergedAt` is the provider timestamp exactly as GitHub reported it, and `delivery.mergedAtRepository` is that instant carried onto the repository clock using `delivery.repositoryClockOffsetMs`, the lower bound of the measured offset. The lower bound is used so the recorded instant is the earliest the merge can have happened and no derived duration is inflated by skew. Every repository-clock comparison — window membership, weekly bucketing, ordering, and the interval from the append-only intent event — uses the repository instant, and it is the merge time the API reports and the interface displays. Deliveries recorded before these fields existed fall back to the provider timestamp, the best reading of the instant available for them. The pulse query filters and orders by exactly that expression, and `events_delivery_repository_instant` indexes the same expression, so the reporting window is an index condition rather than a row filter. The 7-day and 30-day counts include exact merge timestamps at both `now - N days` and `now`. Weekly bars use Monday 00:00 UTC through Sunday 23:59:59.999 UTC, except the current week ends at `now`; both endpoints are inclusive. The API returns exactly 12 weeks.

Intent-to-merge begins at the earliest append-only `create` event for the delivered work item and ends at its exact accepted merge timestamp. The median is the ordinary middle value, or the mean of the two middle values for an even sample. Records missing either endpoint, or with an endpoint in the wrong order, are excluded rather than fabricated. The UI reports both included and excluded sample sizes.

PR-to-production begins at GitHub's durable observed pull-request `createdAt`, splits at the exact accepted merge time, and ends at the earliest successful production deployment that independently records containment of that exact merge SHA. The pull-request creation time is GitHub's clock as well, so it is carried across with the same recorded offset as the merge. Both endpoints of the PR-created-to-merge split therefore shift together and that component is unchanged by the correction, while a pull request created after its own merge on GitHub's clock stays an ordering violation instead of being hidden by a comparison across two clocks. Deployment times come from a third clock, the deployment provider's, and it is related to the repository clock only by measurement. Every observation therefore carries `clockOffset`, the bracket in milliseconds within which the collector measured that provider's clock to stand relative to the repository's: repository instant = provider timestamp + offset, with the true offset somewhere in `[min, max]`. The collector is the only party that sees both clocks, and it measures the bracket the way merge verification measures GitHub's — by reading one clock either side of a read of the other. Ingestion refuses a bracket wider than twenty seconds, the same precision merge verification demands, because a wider one does not locate the deployment on the repository clock well enough to attribute it to an instant; it refuses an inverted bracket, and one placing the clocks more than thirty days apart, which is a misconfigured collector or a replayed report rather than skew. The magnitude of a well-measured offset is not otherwise bounded. Each observation is then carried onto the repository clock once, at ingestion: `deployed_at_repository` is the earliest repository instant the deployment can have occurred at and `deployed_at_repository_max` the latest, and the provider's own `deployed_at` is retained unchanged beside them. A deployment is refused only when even its earliest bound is still in the repository's future, since no reading of the two clocks makes such a report possible; a provider clock running fast is no longer forgiven by a fixed allowance but corrected by the negative offset it measured, so the observation is kept rather than lost until a collector happens to retry.

Every comparison and every published duration uses those repository instants, never the provider timestamp. Reported raw, a provider clock running two hours fast inflates merge-to-production by the whole offset, and one running two hours slow stamps a real post-merge deployment before its own merge, dropping it as unverifiable. A deployment counts as post-merge when its latest bound reaches the merge instant: the containment proof already establishes that it deployed that merge, so a narrower test would discard a real deployment over two clocks each measured to within twenty seconds. Where the two brackets overlap, the merge instant is used as the deployment's own lower bound — it cannot have run before the commit it contains — so the reported instant is clamped to it instead of reading as a negative duration. Published PR-to-production durations are therefore accurate to within the recorded measurement precision of their two endpoints, and the interface says so rather than calling them exact. Normalized provider observations are recorded through `POST /api/production-observations`. Deployment observation is a separate trust lane from acceptance-proof collection: the `producer` role alone does not authorize it, and a producer's `proofs` allowlist confers no deployment authority and is never widened to grant it. The credential must carry an explicit `deploymentProviders` scope naming the exact provider it may report, so a build attestor or test collector that shares the `producer` role cannot forge production-delivery history. A credential with no such scope, an empty one, or one naming a different provider is refused with 403, and implementation workers cannot use this endpoint at all. Each observation retains provider/deployment identity, immutable commit or artifact identity, provider time, the measured clock bracket and both repository instants derived from it, receipt time, source URL, producer, and up to 500 exact contained merge SHAs in append-only indexed tables, so later Railway retention does not erase the history.

The production statistics cover exact merges in the same 12-week UTC reporting window. They report average, median, nearest-rank p90, sample size, coverage, excluded count/reasons, and average PR-created-to-merge and merge-to-production components. Missing GitHub creation observations, missing verifiable containment, superseded deployments, rollbacks, and invalid clock ordering are excluded rather than guessed. A deployment may contain multiple PR merge SHAs. A superseding observation invalidates that deployment; a later valid deployment may become the first endpoint. Samples below five are prominently labeled sparse. Empty metrics are unavailable, not zero-duration.

## Bounds and states

`GET /api/shipping-pulse` is authenticated. It is not offered to operator agents: their API surface is scoped to named work items and cannot serve a repository-wide aggregate, so the navigation entry is hidden for that role rather than leading to a denial. Its event query is bounded by the 12-week index condition and returns at most 1,001 rows; scan cost is proportional to deliveries inside that window, never to total ledger history, plus one indexed single-tuple probe per in-window candidate to settle global deduplication. `production_observation_merges` records both repository deployment instants, the provider time, status, and kind alongside the merge identity, and `production_merges_repository_order` keys `(merge_sha, deployed_at_repository, observation_id)` for successful deployments, so the per-merge lookup reads at most 101 observations in repository-clock deployment order and stops there instead of sorting every mapping for that merge; keyed on the raw provider timestamp the cap would stop at the wrong 101 observations whenever that clock is offset; reaching that overflow marks the response conservatively partial rather than silently claiming complete history. The ingestion request accepts at most 500 merge identities. At most 1,000 deliveries feed metrics, 12 weekly buckets are returned, recent delivery output is limited to 10 records, and each delivery exposes at most 10 policy-violation messages. Quality context is resolved only for those 10 records, and each resolution is a single exact probe of `events_work_revision`, keyed `(work_id, revision, seq)` over event payloads that carry a work document, so it never walks a work item's history. Ordering is merge timestamp descending, then work identity, so equal timestamps are deterministic.

The response is `complete` when the bounded result fits and `partial` when the cap is exceeded. The interface separately presents loading, unavailable, empty, partial, stale, and complete states. Staleness is elapsed time measured by one clock: the browser's own last successful read of the pulse, either because a refresh failed or because more than two minutes passed without one. The repository clock is displayed but never subtracted from a browser clock, so a workstation whose clock disagrees with the repository cannot make fresh data look stale or stale data look fresh. The stale notice offers an explicit retry. Unavailable or absent values are labeled and are never rendered as zero or success. A partial response separates the two effects of the delivery cap rather than describing them together. Only the newest deliveries in the window are read, so the 7-day, 30-day, and weekly counts are lower bounds. The durations are not: median intent-to-merge and the PR-to-production average, median, and p90 describe only those newest deliveries, and the older ones left unread could move them up or down. The response sets `truncated` for that case, and the interface repeats the distinction beside both duration groups so a sampled duration is never read as a conservative bound.

Recent entries link to the exact pull request and merge commit when repository identity is available. Quality context is limited to proof totals and recorded policy violations at delivery.

Proof totals are read from the immutable snapshot the delivery cites in `delivery.authorizationRevision`, located in the event ledger by that exact revision. They are never read from the work item as it stands now, nor from the later state the recording observation happened to carry: a merge observed after its execution expired is authorized from a historical snapshot, so the operator may already have revised requirements or policy by the time the delivery is written, and reporting those newer requirements would restate a properly authorized historical delivery as unproven. The denominator is the distinct required proofs of that snapshot, and the numerator counts only its evidence, applied with the same rules as the acceptance gate: trusted, passing, executed above zero and skipped zero, bound to the exact candidate SHA, base SHA, policy revision, validation selection, and scenario revision, produced by an identity that was not among that snapshot's implementers, and unexpired as of the authorization. Expiry is re-checked at `delivery.evidenceAsOf`, the repository-clock instant the merge authorization itself used, rather than at the provider merge timestamp. The two are different clocks related only through the offset bound captured at merge verification, so when the repository clock trails GitHub a proof can be live at the authorized cutoff and already expired at the raw `mergedAt`; judging it on the provider clock would report a properly authorized delivery as unproven. Merge authorization bounds its execution by the earliest required-evidence expiry, so evidence live at authorization is still live at the recorded instant. Deliveries recorded before this field existed fall back to the merge timestamp. Evidence recorded against a superseded candidate or an earlier policy revision is not counted, so the figure can never exceed the required total. If the cited revision cannot be resolved, the totals are reported as unknown with an explanation rather than as zero of zero.

Policy violations stay with the append-only delivery record itself, so a violation raised by the post-merge comparison against the recorded authorization is still shown. The weekly visual has a screen-reader list with the same values, links and controls are keyboard accessible, and layouts collapse to a single column on narrow screens.
